# 改进方案：对齐上游 TencentDB Agent Memory 规范

> 依据文档：`CONTRIBUTING.md`、`INSTALL.md`（上游 `TencentCloud/TencentDB-Agent-Memory` 仓库）
> 对照项目：`E:\idea work\腾讯记忆链接`（TD 记忆守护 / tencentdb-memory-mcp，v0.5.8）
> 排查时间：2026-09-22

---

## 一、先说结论：这份方案在解决什么问题

本项目与上游是**两种不同形态的集成方式**，不是"上游的残缺版"：

| 维度 | 上游（官方仓库） | 本项目 |
|---|---|---|
| 接入方式 | **Proxy 反向代理**（劫持 `ANTHROPIC_BASE_URL`，改 LLM 请求链路） | **MCP + hook + 后台采集**（不动 LLM 链路，旁路读写） |
| 部署要求 | Docker + 三容器（core 8420 / hub 8125 / knowledge 8424） | 任意已部署的面板，**零 npm 依赖**，单 exe |
| 记忆写入 | Proxy 自动捕获 L0，后台蒸馏 L1/L2/L3 | 守护进程扫本地会话文件**增量上传** |
| 记忆读取 | Proxy 每轮自动注入 L2/L3 + 技能 + 知识 | hook 强制注入 + MCP 11 个只读工具按需检索 |

**所以本项目的定位是"轻量旁路接入层"，这是它的核心价值，不该被改成 Proxy 形态。**

但正因为是旁路形态，在**工程规范**上确实存在与上游的落差。下面按 P0/P1/P2 分级。

## 二、P0 — 必须修（正确性 / 会被用户或 CI 直接踩到）

### P0-1　`package.json` 缺 `engines`，且 Node 版本声明自相矛盾

**证据**
- `CONTRIBUTING.md`：`Node.js ≥ 22.16.0`
- 本项目 `package.json` / `pet/package.json`：**均无 `engines` 字段**
- `README.md` 第 3 行：`纯 Node ≥16`；第 187 行：`本机 Node 16 无 fetch 也能跑，推荐 Node ≥18`
- 但 `pet/src/sessions.js` 用 `require('node:sqlite')` —— **这是 Node 22 才有的内置模块**

**问题**：README 说 ≥16 可用，实际桌面端依赖 Node 22 的 `node:sqlite`（虽然 `try/catch` 降级了，但降级后"实时会话"功能静默失效，用户只会看到"最近交互停在几个月前"，属于**上一轮刚修过的同类 bug 的复发路径**）。

**改法**
1. 两个 `package.json` 加 `"engines": { "node": ">=22.16.0" }`（对齐上游基线）
2. README 的版本声明分场景写清楚：
   - 守护进程 / MCP（零依赖，走 http/https）：`≥16`（Node 18+ 有 fetch 更好）
   - 桌面应用（Electron，含 sqlite 会话源）：`≥22.16.0`
3. 在 `sessions.js` 的降级分支加**显式告警**（而非静默返回空）：
   当前 `_sqliteCache.error = 'node:sqlite 不可用'` 已被记录，但从未上报到 UI —— 应让控制台"实时会话"区显示"会话库不可读（Node 版本过低？）"，把静默降级变成可见告警。

### P0-2　缺 `LICENSE`，但代码/文档已声明 MIT

**证据**
- `CONTRIBUTING.md`：`By submitting a contribution you agree that it will be licensed under the project's MIT License`
- 本项目根目录：**无 `LICENSE` 文件**（`ls LICENSE*` 无输出）

### P0-3　`register.js` 与 `register-all.cjs` 的客户端清单已分叉（双真源）

**证据**
- `pet/src/register.js` 的 `CLIENTS`：`zcode / claude-code / cursor / codex / trae / deepseek-harness`（6 个）
- `register-all.cjs`（源码用户入口）：**独立实现**，未从 `register.js` 复用
- 上游 `INSTALL.md` 列的 agent 客户端：Claude Code / CodeBuddy / WorkBuddy / Codex / DeepSeek Harness / OpenCode / Hermes / OpenClaw / Pi（**9+**）

**问题**：这是上一轮审计确立的**"检测面 vs 写入面必须同源"**原则的又一个实例——只不过这次是"桌面端清单 vs 源码端清单"两套。两份清单一旦漂移，同一台机器用 exe 接入和用源码接入会得到不同结果，正是上一轮修掉的 hook 判据矛盾的翻版。

**改法**
- 把 `CLIENTS` 抽成**单一真源**（如 `core/clients.js`），`register.js` 与 `register-all.cjs` 共同 require
- 若短期不想重构，至少在 `register-all.cjs` 顶部注释标明"清单需与 `pet/src/register.js` 的 CLIENTS 手动同步"，并加一条一致性测试断言两者 key 集合相等

### P0-4　CI 只做冒烟，未跑完整测试套件

**证据**
- `.github/workflows/release.yml` 的"冒烟自检"只跑：
  `node daemon health`、`node mcp list`、`test/register.test.js`、`test/functional.test.js`
- 项目实际有 **12 个测试套件**（`test/` 下 12 个文件），`test:all` 串起 13 个环节
- `CONTRIBUTING.md`：`Tests: add tests with new features; fix a bug with a regression test first`；提交流程要求"run the relevant tests"

**问题**：发版流水线**不跑 `test:all`**，等于把 `renderer-dom.test.js`（id 唯一性）、`verify-v3-skin.cjs`（CSS 令牌）、`guard-off`（守护停止态）、`takeover` 等 9 个套件全部漏掉。上一轮审计里发现的"CSS 裸圆角被 `verify-v3-skin.cjs` 拦下""id 冲突被 `renderer-dom.test.js` 抓到"这类问题，在发版时**不会被拦**，会直接进 Release。

**改法**
1. 新增 `.github/workflows/ci.yml`：`on: [push, pull_request]`，跑 `npm ci --prefix pet` + `npm run test:all`
2. `release.yml` 的冒烟步骤升级为 `npm run test:all`（或至少补齐 `renderer-dom.test.js` + `verify-v3-skin.cjs` 两个纯静态、无需浏览器的套件）
3. `test:all` 里的 `make-preview.cjs` 是生成步骤（非校验），CI 里可拆出 `test:ci` 只跑校验类，避免无谓产物

### P1-4　面板 API 只认 `/api/v1`，与上游文档的 `/v3/*` 不一致（需确认）✅ 已实测确认并落地

**证据**
- `core/tdai-core.js`：`const url = cfg.panelUrl + '/api/v1' + pathname;`
- 上游 `INSTALL.md` 全文用的是 `/v3/meta/*`、`/v3/analytics/*`，`INSTALL.md` 明确说 `POST /v3/meta/auth/verify`

**问题**：这可能**不是 bug**（面板的 `/api/v1` 是业务面、`/v3/` 是 meta 面，两者并存），但**文档里没有任何说明**。一旦面板升级只保留 `/v3`，本项目会静默 404。

**✅ 实测结论（2026-09-22，对真实面板 `http://muhuihao.top:8125`）：**

| 请求 | 结果 |
|---|---|
| `POST /api/v1/skill/list` | **200** `{"code":0,...}`（返回 33 条） |
| `POST /api/v1/chat-memory/search` | **200** `{"code":0,...}` |
| `POST /api/v1/meta/auth/verify` | **200** `{"code":0,"data":{"valid":true}}` |
| `POST /v3/skill/list` | **404 Not Found** |
| `POST /v3/meta/auth/verify` | **404 Not Found** |
| `POST /v3/chat-memory/search` | **404 Not Found** |
| `POST /v3/analytics/overview` | **404 Not Found** |
| `GET /v3` | **200**（返回前端 SPA 的 `index.html`） |
| `GET /api/v1` | 404 |

→ **`/v3` 是前端路由，不是 API 前缀**。本项目走 `/api/v1` 业务面**完全正确**，
上游文档里的 `/v3/*` 属于另一套（meta/analytics）面且本面板未提供。
**结论：不需要版本协商**（回退到 `/v3` 只会得到 404，反而掩盖真实错误）。

**已落地**
1. `core/panel-codes.js` 新增 `API_PREFIX = '/api/v1'` 作为**唯一真源**（含上述实测记录）
2. `core/tdai-core.js` 顶部注释写明 "/v3 是前端路由，别把这里对齐成 /v3"
3. daemon 内联 `PANEL_API_PREFIX`（SEA 单文件要求），`test/panel-codes.test.js` ⑧ 断言两处都是 `/api/v1`
4. `INSTALL.md` Q2 增加「面板没有这个接口」一行（面板版本不匹配时的自查）

### P1-5　错误提示未对齐上游的 status code 语义 ✅ 已完成（并发现更严重的问题）

上游 `INSTALL.md` 给出明确的业务错误码：`permission_denied`、`409`（重名）、`404 analyse_marker_disabled`、`503`（`KNOWLEDGE_ANALYTICS_ADMIN_KEY` 未设）。

本项目 `core` 的 `api()` 只处理 HTTP 层的 401/403/5xx，**未解析面板返回体里的业务 `code`**。用户拿到一个失败，只能看到 `HTTP 200` + 无从解释的 `raw`。

**✅ 实测发现（比原判断严重得多）：** 面板不是「HTTP 状态码即结论」，而旧实现会把**真失败判成成功**：

| 情况 | HTTP | body | 旧实现判定 |
|---|---|---|---|
| 缺 `X-Tdai-Service-Id` | 400 | `MISSING_INSTANCE_ID` | ~~ok~~ ❌ |
| 缺 `X-Tdai-User-Key` | 400 | `MISSING_USER_KEY` | ~~ok~~ ❌ |
| `serviceId` 不存在 | 400 | `INVALID_INSTANCE` | ~~ok~~ ❌ |
| 检索没给 `block_id` | 400 | `MISSING_BLOCK_ID` | ~~ok~~ ❌ |
| 分层传非法 `layer` | 400 | `INVALID_LAYER` | ~~ok~~ ❌ |
| 端点不存在/方法不对 | 404 | 纯文本（**无 JSON**） | ~~ok~~ ❌ |
| 检索用错 userKey | 401 | `INVALID_USER_KEY` | ok ✅ |

**附加发现（本次最严重的 bug）：** `/skill/list` 与 `/meta/auth/verify` 对**坏 userKey**
都返回 `HTTP 200 + code:0`（**不校验**）；只有检索面接口（`/chat-memory/*`）会真校验并回
`401 INVALID_USER_KEY`。而三处探活（core `health()`、daemon `/api/test-connection`、
pet `testConn()`）全都打 `/skill/list` 且写 `auth = nas` → **`auth` 恒等于"面板可达"，
永远发现不了 Key 失效**。表现：界面显示"连接正常"，实际所有检索与上传都在静默失败。

**已落地**
1. 新增 **`core/panel-codes.js`（唯一真源）**：`PANEL_OK_CODE` / `PANEL_HINTS`（14 个码 → 中文可操作提示）
   / `PANEL_CODE_CLASS` / `codeKeyOf()` / `classify()` / `summarize()` / `API_PREFIX`
2. `classify()` **业务码优先于 HTTP 码**，分 `ok / auth / input / not-found / server / unreachable / unknown`
   七类，并带 `retriable`；404 显式暴露（不再静默当成功）
3. `core/tdai-core.js` `api()` 改用 `classify()`；`ok()/err()` 支持第三参携带 `panel` 判定结果
4. **三处探活端点统一改为 `/chat-memory/my-agents`**（真校验 key），
   `nas`（面板活着，含 4xx）与 `auth`（真鉴权通过）**分开判定**
5. daemon `mkApi()` 挂 `v`/`ok`；`uploadBatch` / skill 缓存 / recall 组装 / `/health` / `test-connection`
   全部改判 `ok`；daemon 内联副本 + 测试断言与 core 语义一致
6. `pet/src/main.js` `_onHttp` 新增 `panelAuthFail`（401/403），顶栏 pill 分
   「认证失败」（指向重新签发 userKey）与「连接失败」（指向改地址）；连接测试按钮三态提示
7. 新增 **`test/panel-codes.test.js`（107 断言）**：真值表驱动 + 双份副本一致性 + 探活端点回归
8. `INSTALL.md` Q2 重写为三态表格 + 「为什么 key 失效能单独报出来」的实测说明

## 四、P2 — 可以做（增强 / 长期价值）

### P2-1　客户端覆盖缺口：6 vs 9+

上游 `INSTALL.md` 支持 9 类 agent；本项目 `CLIENTS` 覆盖 6 个（zcode / claude-code / cursor / codex / trae / dsh）。

**缺口**：`CodeBuddy`、`WorkBuddy`、`OpenCode`、`Hermes`、`OpenClaw`、`Pi`。

**优先级判断**：
- **CodeBuddy / WorkBuddy**：配置路径上游已明确（`~/.codebuddy/models.json`、`~/.workbuddy/models.json`），若做 MCP 接入需确认其 MCP 配置格式 → **建议优先**
- **OpenCode**：`~/.config/opencode/opencode.json`，格式已知 → 容易加
- **Hermes / OpenClaw**：上游文档自己标注了 `x-task-id` / `x-conversation-id` 的**已知限制**，走 header preselect，接入复杂度高 → 暂缓
- **Pi**：走 `pi-plugin` 扩展 + env 变量，**与本项目的 MCP 旁路形态天然契合**（都是"不动 proxy 链路"的思路）→ 值得评估

**改法**：先用 P0-3 的单一真源重构，之后每个新客户端只是往清单里加一项，边际成本低。

---

### P2-2　无端到端「真实面板」集成测试

`test/e2e-live.test.js` 实测用的是 mock 面板。上游 FAQ 建议用 `/health` 的 `services.pipelineWorker` 观察管线是否在工作（`curl -s http://localhost:8420/health | jq .services.pipelineWorker`，看 `tasksConsumed`/`tasksCompleted` 增长）。

**已落地（改为 CI 常驻 + 更强）**：不联网、不依赖真面板凭据的前提下，`test/panel-contract.test.js` **本地起一个 HTTP 服务精确复刻真面板行为**，再让**真实的** `core.health()` / `memorySearch` / `memoryLayers` 以及 **真实 spawn 的 daemon 进程**去打它。
覆盖 6 组共 41 项：
1. `classify()` 对**真实 HTTP 响应体**的判定（成功 / 401 / 400 业务码 / 纯文本 404 / 空响应）
2. `core.health()` 的 `nas` / `auth` 解耦 —— 断言坏 key 时 **`nas=true` 但 `auth=false`**（旧代码此处恒为 `true`）
3. **真实 daemon 进程**（`spawn` + 假 HOME）的 `/api/test-connection` 与 `/health`
4. `core.health` 打的是 `/chat-memory/my-agents`，且**不依赖** `/skill/list` 做认证判据
5. 非法 `layer` 被本机拦下（不静默成功）
6. `API_PREFIX = /api/v1`；`GET /v3` 返回 HTML（前端 SPA）而 `POST /v3/skill/list` 是 404

**关键设计**：夹具里**刻意保留**了"`/skill/list` 与 `/meta/auth/verify` 对坏 key 也返回 HTTP 200 + `code:0`"这个真实陷阱 —— 如果哪天有人把探活端点换回 `/skill/list`，④ 组会立刻红。
另外 `clients-consistency.test.js` ⑩ 把 core 与 daemon 内联副本用**同一批 12 组响应体**逐字段比对（`key` / `kind`），双副本漂移再也无法静默发生。
